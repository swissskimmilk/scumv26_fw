# scumv26_fw

Firmware for the SCuMV26 bring-up board: an STM32U575VIT6 (LQFP-100) that powers, clocks,
monitors and captures from the SCuMV26 DUT, driven from a PC over USB.

The MCU is a dumb, reliable instrument; test logic lives in Python on the PC
(`host/scum.py`). Bare-metal superloop: interrupts and DMA do the time-critical work,
`app_loop()` does the rest.

## Layout

| Path | What | Who edits it |
|---|---|---|
| `scumv26_fw.ioc` | CubeMX config: pinout, clock tree, peripheral setup. **Master copy.** | CubeMX GUI, or by hand + regenerate |
| `Core/`, `Drivers/`, `cmake/`, `startup_*.s`, `*.ld` | generated by CubeMX | CubeMX only (except `USER CODE` blocks) |
| `App/` | all application code | us |
| `App/usb/` | TinyUSB config + CDC descriptors | us |
| `lib/tinyusb` | TinyUSB 0.20.0 (git submodule) | upstream |
| `host/scum.py` | PC tool and Python API | us |
| `CMakeLists.txt` | top-level build (CubeMX writes it once, never again) | us |

`main.c` only calls `app_init()` and `app_loop()` from its `USER CODE` blocks, so
regenerating never touches application code.

## Build and flash

Uses the GCC 13.3 toolchain and STM32_Programmer_CLI bundled with STM32CubeIDE (found
automatically under `C:\ST`), plus CMake and Ninja on PATH.

```powershell
git submodule update --init
.\build.ps1            # Debug build -> build\Debug\scumv26_fw.elf
.\build.ps1 -Flash     # build, then program over SWD (ST-Link on the 10-pin header) and reset
```

Debugging: open the folder in VS Code with the STM32 extension (or CubeIDE: File > Import >
CMake project); SVD for the register view is in the CubeIDE install.

## Changing the hardware config

Edit `scumv26_fw.ioc` in the CubeMX GUI and press Generate, or regenerate headless:

```
STM32CubeMX\jre\bin\java -jar STM32CubeMX.exe -q gen.txt
```
with `gen.txt`:
```
config load C:\Users\aidan\scumv26_fw\scumv26_fw.ioc
project toolchain CMake
project setCustomFWPath C:\Users\aidan\STM32Cube\Repository\STM32Cube_FW_U5_V1.9.0
project generate
exit
```

Notes from setting this up:
- The firmware pack is STM32CubeU5 v1.9.0 from GitHub (HAL + CMSIS only, sparse clone).
  CubeMX's own downloader needs an ST login; `setCustomFWPath` avoids it.
- Use backslash paths in CubeMX scripts; forward slashes break its file joins.
- USB is deliberately **not** enabled in the `.ioc`: TinyUSB owns the OTG_FS core and sets up
  PA11/PA12, HSI48 and the CRS itself (`App/host_link.c`). Enabling it in CubeMX makes
  headless generation stall on an "IP not ready" dialog.
- DMA, DCMI capture control, TIM6 and the USART1 interrupt are configured in `App/`, not
  the `.ioc`.
- Headless CubeMX does not run the I2C timing calculator: it writes `Timing = 0`. The `.ioc`
  therefore pins `I2C2.Timing=0xF0C22731` (100 kHz from 160 MHz) with `CustomTiming=Enabled`.
  Recompute it if the I2C clock or speed changes.
- If a headless run prints nothing after `project generate`, a stale `java.exe` from an
  earlier run is holding CubeMX's lock; kill it and rerun.

## Commands

Every reply ends with `OK` or `ERR <reason>`. Lines starting with `!` are asynchronous
events (over-current trip, reset button); they are lost if no host is connected, but every
event is also counted for `status`. Capture headers carry a CRC-32 of the data, which
`scum.py` checks against `zlib.crc32`.

```
help                                 list commands
status [peek]                        event counters since the last read: over-current trips (which
                                     rails), capture errors, dropped UART/host bytes, button resets,
                                     MCU reset cause, uptime; cleared on read unless `peek`
power up | down                      sequenced: VIO -> VBAT -> 1V rails (reverse for down)
rail [vio|vbat|1v on|off]            single regulator enable
sw [vddd|vdda|rf board|dut]          rail-source switches
vbat [volts]                         open-loop VBAT set point via the DAC (1.16-1.55 V, buffered DAC)
trim <volts>                         closed-loop VBAT on its INA237 reading (to 1 mV)
dac [code]                           raw DAC code
tele                                 Vbus, current, Vshunt for all six INA237s
ilim [rail mA]                       hardware over-current trip per rail; any trip drops all rails
aux                                  TLA2528: VNFC, PWR_BG, PWR_TEST_0, PWR_I_REF, VIO, PWR_VDD_RF, SPARE_1/2
i2c scan
clk [sel dig|ana|off] [psc 1|2|4|8] [win ms]
freq                                 DUT clock frequency from the latest window
adc init | reset | rd <a> | wr <a> <v> | mode ddr-a|ddr-b|sdr-a|sdr-b | pat <a> <b> | pat off
cap <words>                          capture into SRAM, then dump (up to 98304 words)
uart baud <n> | tx <text> | rx       DUT UART bridge
pin [name [0|1]]                     read or drive any DUT control pin by name
pulse <name> <us>                    pulse a pin away from its idle level
```

```powershell
pip install -r host\requirements.txt
python host\scum.py                     # interactive
python host\scum.py power up
python host\scum.py cap 65536 -o iq     # -> iq.npz
```

## How the hard parts work

- **Clock counting** (`clk_count.c`): TIM2 counts PA0 edges in hardware via ETR (with its
  /1-/8 prescaler); TIM6 interrupts once per window at top priority and latches the
  count. No per-edge CPU work. Prescaled input must stay under 40 MHz (TIM2CLK/4), so the
  default `psc 4` covers inputs up to 160 MHz.
- **I/Q capture** (`adc_capture.c`): DCMI 10-bit, external sync, snapshot mode. GPDMA1
  channel 12 walks a linked list of 32 KiB nodes from DCMI->DR into a 384 KiB SRAM buffer
  with no CPU involvement; the CPU only starts it, waits for the final transfer-complete,
  then streams the buffer over USB (~1 MB/s, so ~0.4 s per full capture).
- **Over-current**: each INA237's shunt-over-limit drives the shared ALERT line; its EXTI
  handler drops every DUT enable before anything else runs.

## Open items (need hardware or a decision)

1. **One channel per capture (decided).** The dual ADC3910 cannot put both channels on
   rising edges at the full rate (TI, E2E 1490292; SDR outputs one channel, chosen by
   SDR_CHB_SEL), and DCMI latches one edge. `ddr-a`/`ddr-b` work from ADC reset (DCMI edge
   flip); `sdr-a`/`sdr-b` hold each sample a full DCLK period and are preferred once SPI
   works. Verify each mode with `adc pat 0x1555 0x2AAA` + `cap`: you should see only that
   channel's constant. I and Q are captured separately, so their relative phase is lost.
2. **HSYNC/VSYNC loopback**: PD12 -> PD8 and PD11 -> PB7 must be wired on the board
   (10-bit DCMI only supports external sync).
3. **ADC bit order**: the output bit mapper is left at reset defaults. Confirm D2..D11 order
   with constant test patterns before trusting data.
4. **GPDMA bandwidth** at 32 MHz DCLK (64 MB/s into SRAM) is untested; `cap` reports DCMI
   overruns explicitly.
5. **CORE_RST polarity** is unconfirmed; the pin idles high (matching the fitted pull-up)
   and `pulse`/the button pulse away from whatever level it is at.
6. **TileLink and scan chain** are exposed as raw pins (`pin`, `pulse`) for scripting from
   the PC; protocol-level bit-banging in firmware is not written yet.
7. **VBAT range** is 1.16-1.55 V, not the network's 1.11-1.60 V, because the DAC output
   buffer only swings 0.2 V to VREF+ - 0.2 V. Unbuffered would reach the full range, but its
   source impedance sits in series with the 36.4 k and makes the set point load-dependent.
8. Nothing here has run on hardware yet. It builds warning-clean (`-Wall -Wextra`) against
   HAL 1.9.0.
